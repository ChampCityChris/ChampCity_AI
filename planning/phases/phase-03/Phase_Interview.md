## Architect Clarification Decisions

### 1. What is the primary UI model for Phase 03?

Options:

- A. Keep the existing screen-picker layout and add explanatory labels.
- B. Keep navigation, but make a computed current-action route the primary experience.
- C. Replace all secondary navigation immediately.

Architect recommendation: B.

Decision: Phase 03 should make the current required action the primary route while preserving secondary/manual navigation as fallback. Full removal of secondary navigation is premature and could trap the Operator if state detection is wrong.

### 2. What determines the current required action?

Options:

- A. The screen the Operator last opened.
- B. The first incomplete step in the locked workflow as inferred from durable artifacts and status records.
- C. A user-selected dropdown.

Architect recommendation: B.

Decision: Current action must be computed from durable project state: project artifacts, roadmap phase statuses, phase bundle approval records, Work Card status, Implementer Reports, Architect review outcomes, Validation Records, repair sub-cards, closeout records, roadmap update state, and activation state.

### 3. How should workflow visibility be represented?

Options:

- A. Full draw.io map embedded as the main UI.
- B. A left-to-right workflow strip or progress map that highlights the current step and visible loops.
- C. No workflow map; only a task card.

Architect recommendation: B.

Decision: Add left-to-right workflow visibility where useful, but do not make the visual map the workflow authority. The map is explanatory; durable state is authoritative.

### 4. How should artifact work be presented?

Options:

- A. Separate artifact screens chosen manually.
- B. A current action workspace that shows the relevant artifact, source context, expected output, and next decision.
- C. Raw file browser only.

Architect recommendation: B.

Decision: Phase 03 should introduce an artifact review workspace tied to the current workflow step.

### 5. How should repair routing work?

Options:

- A. Failed validation routes back to the original Work Card without a new record.
- B. Failed validation creates a `WCxx-REPAIRxx` sub-card route.
- C. Failed validation closes the phase as failed.

Architect recommendation: B.

Decision: Repair routing must use `WCxx-REPAIRxx` sub-card naming and remain visible as part of the Work Card Loop.

### 6. How should MCP/direct-write failure be handled?

Options:

- A. Block the workflow until MCP works.
- B. Preserve manual fallback paths while clearly showing degraded mode and copy/paste instructions.
- C. Ignore write failures and continue.

Architect recommendation: B.

Decision: Manual fallback must remain available where MCP/direct write is unavailable. The UI must show when the app cannot write directly and what artifact the Operator must create or paste manually.

## Phase Interview Summary

Phase 03 should correct the app screens around workflow routing. The phase should not perform generic UI polish. It should install a state-driven current-action model and refit the visible UI around the locked workflow.

The phase must preserve the Architect / Implementer / Operator role separation:

- Architect creates phase mapping, full Work Cards just in time, Implementer Report reviews, validation steps, repair sub-card drafts, and closeout recommendations.
- Implementer executes approved Work Cards and returns Implementer Reports.
- Operator approves phase mapping, reviews Work Cards, validates implementation, records validation outcomes, and approves closeout/activation decisions.
